## Что уже закрыто — не переоткрывать

**Слой состояния игры.** `IngameStateOffsets.Data = 0x218`, `.Camera = 0x270` (указатель, не
встроенная структура). `IngameDataOffsets` целиком: `CurrentArea 0xB0`, `CurrentAreaLevel 0xD4`,
`CurrentAreaHash 0x114`, `MapStats 0x128`, `LabDataPtr 0x48`, `ServerData 0x968`,
`LocalPlayer 0x970`, `EntityList 0xA28`, `EntitiesCount 0xA30`, `SleepingEntityList 0xA38`,
`SleepingEntityCount 0xA40`, `Terrain 0xC08`, `EnvironmentData 0x1110`. `TerrainData` перемерена
целиком. Проверено в четырёх зонах и после перезапуска клиента.
Подробности — `docs/offsets.md`, сырые замеры — `docs/api/ingamedata-measured.md`.

**Слой сущностей.** Путь метаданных `details+0x08` со длиной `details+0x18` (критерий сошёлся
141 из 141 и держится в трёх зонах); вектор компонентов `ent+0x10`; `Id 0x88`; `IngameData 0x78`;
прямой указатель на `Positioned` по `ent+0x98`. Устройство слот‑таблицы (`details+0x28` →
`lookup+0x40`, адрес компонента `= [comps.First + index*8]`) подтверждено содержимым.

**Ключ типа компонента — vtable самого компонента**, `[компонент+0x00]` в виде RVA.
Таблица `GameOffsets/ComponentVtables.cs` — 40 пар. `nameId` из слот‑таблицы **опровергнут**:
13 из 25 названных типов несут больше одного `nameId`, у `BaseEvents` их три, все разности кратны
`0x100`; обратно, один `nameId 0x1D8` носят `Chest` и `WorldItem`. Слот‑таблица оставлена как
независимый контроль (число непустых слотов равно числу компонентов), но для опознания типа
не нужна.

**Горячий путь.** `Positioned.GridX/GridY = 0x294/0x298` — **int32, не float**;
`WorldPosition 0x2B8`. `Render.Pos 0x120`, `Bounds 0x12C`, `Name 0x148` (встроенная строка, длина
`0x158`, ёмкость `0x160`). `Life` — три блока, голова каждого указывает на сам компонент:
HP `0x1A4/0x1A8`, мана `0x1F4/0x1F8`, щит `0x23C/0x240`.

**Предметы.** Компоненты предмета живут не на сущности зоны, а на предметной сущности по
`WorldItem + 0x28` (замерено 14 из 14), и у неё **своя vtable**.

**Прочее.** `ServerData.Latency = 0xC490` (старое `0x6CA0` читало `0x128CBA26`).
`FilesContainer.FindFile` больше не роняет хост. Починен критический баг: `EntityList` читал `Id`
по литералу `0x50` при `IdOffset 0x88`, из‑за чего список сущностей движка оставался бы пуст.

Протокол замера слоя сущностей — **`docs/api/entities-measured.md`, читать первым.**
`docs/api/survey-2026-09-16.md` — обследование, с которого всё началось; ценно как след времени,
но два его утверждения опровергнуты, и об этом там есть врезка.

## Инструменты

**`tools/EntCap`** — атомарный снимок слоя сущностей. Вся цепочка читается в ОДНОМ процессе,
снимок обрамлён проверкой «зона и база `Data` не менялись» (код 3 = НЕДЕЙСТВИТЕЛЕН).
Намеренно не ссылается на `GameOffsets`: он обязан уметь читать гипотезу, которой в коде ещё нет.

    FindOffset.exe --ingame-state            # адрес IngameState, он стабилен до перезапуска игры
    EntCap.exe --igs <адрес> --byvtbl        # компоненты по vtable + контроль ent+0x98
    EntCap.exe --igs <адрес> --comp          # Positioned / Render / Life, каждый со своим критерием
    EntCap.exe --igs <адрес> --items         # спуск в предметную сущность
    EntCap.exe --igs <адрес> --watch 90      # накопление за время: снаряды, эффекты, редкие типы
    EntCap.exe --igs <адрес> --raw --slots --posdump

**`tools/RefLive`** — оракул: подключает `ExileCore.dll` эталона и читает его члены рефлексией.

    RefLive.exe                              # обзор адресов
    RefLive.exe --as <Тип> <адрес> --only X  # натравить ПАРСЕР эталона на наш адрес
    RefLive.exe --harvest N                  # имя компонента ↔ наш слот ↔ RVA vtable, join ПО АДРЕСУ

`--harvest` — главный приём добора таблицы типов: соединение идёт по адресу компонента, ни имена,
ни `nameId` в нём не участвуют. `--as` — когда оракул не может назвать адрес сам; **всегда с
контролем**: тот же разбор по заведомо чужому адресу обязан дать бессмыслицу.

> **Оговорка, которая стоила прежнему промту ложного утверждения.** Для `Element` этот контроль
> НЕ РАБОТАЕТ. Прежний текст называл контролем подпись `ChildCount = −1572032` — но это значение
> самого кандидата, а произвольный чужой адрес (например камера) даёт бессмыслицу ТОЙ ЖЕ ФОРМЫ:
> `Children: 0` и мусорный хэш. Различить ими нельзя ничего. Для UI нужен другой различитель, и
> он ПОЯВИЛСЯ: камера починена, значит `Element.GetClientRect` больше не отдаёт NaN и прямоугольник
> кандидата снова что‑то значит. См. «Порядок работ», пункт 6.

**`tools/CamCap`** — атомарный снимок КАМЕРЫ. Не проверяет подставленное число, а ИЩЕТ смещение
по самопроверяющемуся критерию. `--dump`, `--watch N` (контроль ходьбой), `--len N`.

**`tools/FindOffset`** — `--find` (где в окне лежит значение), `--window` (дамп с пояснением),
`--chain`. **`tools/dumpdiff.py`** — разность двух дампов одного окна, имеет смысл только в одной
зоне. **`tools/measure-ingamedata.sh`** — атомарная рамка для слоя `IngameData`.

## Метод

**Атомарность.** В игру играет человек: между двумя соседними командами меняется зона, и адрес из
первой команды начинает указывать в память другой зоны. Это не теория — первая же попытка мерить
слой сущностей отдельными командами дала дамп `Data+0xA28` из одних float. Либо `measure-ingamedata.sh`,
либо один процесс, который сам себя обрамляет (как `EntCap`). **Не принимай ни одного числа,
полученного без такой рамки.**

**Подтверждение содержимым сильнее поиска по окну.** Единственность — свойство ОКНА, а не поля.
Работают самопроверяющиеся критерии, которые неверное смещение не может выполнить случайно:

* длина строки равна полю длины (так закрыт путь метаданных — 141 из 141);
* `world / grid = 10.87` по обеим осям (так закрыт `Positioned`);
* голова блока содержит указатель НА САМ КОМПОНЕНТ (так опознаны блоки `Life`);
* `[компонент+0x08]` равен адресу своей сущности;
* число непустых слотов равно числу компонентов;
* совпадение с фактом, известным ВНЕ памяти (у персонажа Chaos Inoculation → `HP 1/1` и большой
  щит; имя `Render.Name` совпадает с тем, что видно в игре).

**Выборка из трёх сущностей — не выборка.** `InventoryId +0x70` совпадал на трёх и развалился на
сорока: у сундука там лежит указатель в модуль игры. Прежде чем вносить число, прогони его по
всей зоне и по разным ВИДАМ сущностей.

**Корреляция по видам сущностей сужает, но не называет.** «Этот компонент есть только у оружия» —
сильная улика, но имя даёт только оракул.

## Порядок работ

Порядок задан ЗАВИСИМОСТЯМИ и ЦЕНОЙ, а не ценностью. Сначала то, для чего числа уже сняты;
потом то, что требует охоты; UI — последним, и по причине, которая ниже названа явно.

**Важная рамка, без которой половина выводов читается неверно.** Обычный `build.bat` плагина
собирает его **против эталона, а не против форка**. Он определяет корень тремя уровнями вверх от
себя; для нынешнего расположения это `D:\`, где `ExileCore.dll` нет, поэтому срабатывает откат на
`ExileApi-Compiled` (строка `if not exist "%EXILE_ROOT%\ExileCore.dll"`). Переменная окружения
`EXILE_ROOT` имеет приоритет и это поведение отменяет.

Выход сборки форка при этом СУЩЕСТВУЕТ — `D:\deferred\PoeHelper\ExileCore.dll`, — и гейт
`ForkCompat` собирает плагин против ОБОИХ корней. То есть форк проверяется, но не он
подхватывается обычной сборкой.

Следствие для приоритетов: ни одна из описанных ниже поломок не «происходит прямо сейчас» в
продакшне — все они про день, когда форк подставят вместо эталона. Это уравнивает доводы «бот
действует неверно» и «бот бездействует»: и то и другое про один и тот же будущий день, и выбирать
между ними надо по ЦЕНЕ и ЗАВИСИМОСТЯМ, а не по драматичности отказа.

### 0. Нулевым ходом — отдать владельцу список просьб

Чтобы к концу работы по коду замеры были возможны. Просьбы копить и отдавать СПИСКОМ:

0. **походить 15 секунд**, пока идёт `CamCap.exe --igs <адрес> --watch 25` — разводит копии
   матрицы `0x1A8`/`0x1E8` и двойник `Position`. Самая дешёвая просьба из всех, совмещается с любой
   из следующих;
0б. **сменить разрешение или размер окна игры** и повторить `CamCap.exe --igs <адрес>` — разводит
   двойник `Width/Height` (`0x318` против `0x498`);
1. зона с монстрами, постоять в ней (`ObjectMagicProperties.Rarity`);
2. **союзный монстр** в кадре — миньон, тотем, спектр (`Positioned.Reaction`);
3. зона со святилищем (`Shrine`);
4. пройти мимо закрытого сундука и открыть его (`Chest.IsOpened`, парные состояния).

### 1. Камера — ЗАКРЫТА 2026‑09‑17

Была сломана полностью; починена замером. Числа: `Width 0x318`, `Height 0x31C`,
`MatrixBytes 0x1A8`, `Position 0x2E8`, `ZNear 0x308` (новое поле), `ZFar 0x30C`.
Протокол — **`docs/api/camera-measured.md`**, инструмент — **`tools/CamCap`**.

Контроль сошёлся: проекция позиции игрока даёт горизонтальный ЦЕНТР экрана с ошибкой `0.0000` px.
Гейт `SanityRead` получил раздел «7. КАМЕРА» — первый его раздел, проверяющий СОДЕРЖИМОЕ поля, а не
диапазон числа; прежние смещения дали бы на нём промах в 1280 px.

**Что из прежнего текста этого пункта оказалось неверным — и это важнее, чем что оказалось верным:**

* `Position` НЕ равен «матрица + `0x34`». Эта гипотеза (она и была помечена как непроверенная)
  опровергнута: по `0x1DC` лежит строка переноса самой матрицы. Истинное положение камеры — `0x2E8`,
  и оно не списано, а вычислено обращением матрицы и затем найдено в памяти.
* `ZFar` не пришлось оставлять «помеченной гипотезой» — обе плоскости выведены из матрицы и найдены.
* «`Width = 0` даёт **NaN для любого элемента**» — верно только для `X` и `Width` прямоугольника.
  `Y` и `Height` выходят КОНЕЧНЫМ мусором (`−10027651`, `−5730086`), а конечное значение проходит
  любую проверку на `IsFinite`. По той же причине не работают сторожа вида `if (r.Width <= 0)`:
  `NaN <= 0` есть `false`.
* Правка смещений класс NaN‑ошибок НЕ закрывает: `IngameState.Camera` никогда не `null`
  (`GetObject` отдаёт объект с `Address = 0`, `Memory.Read<T>(0)` отдаёт нули), поэтому на
  логин‑экране и в переходе зоны `Width` снова 0 — уже при верных смещениях. Поэтому в
  `Element.GetClientRect` добавлен явный страж.

**Осталось незакрытым, обоим нужен владелец, оба дешёвые** (см. список просьб):

* копии матрицы `0x1A8` и `0x1E8` совпадают ПОБАЙТНО в покое (807 опросов — ноль различий);
  разводит только ходьба во время `CamCap --watch`;
* у `Width/Height` есть двойник `0x498/0x49C`, у `Position` — двойник `0x420`; по значению
  неразличимы. Первую пару разводит смена разрешения, вторую — та же ходьба.

### 2. Пакет «числа уже сняты» — одной правкой, владелец не нужен

* **`Targetable`: база `0x30 → 0x50`.** По `+0x50` лежат байты `01 01 00`, и оракул на том же
  адресе даёт `isTargetable True, isTargeted False` — единственная база, дающая эту пару.
  Разблокирует `Entity.IsTargetable`. Контроль: оракул обязан дать `True/False`, а не `True/True`.
* **Файловый реестр: `fileRoot+0x8 → +0x0`.** По `+0x8` ноль, по `+0x0` живой указатель в кучу,
  поэтому словарь файлов сейчас пуст. Числа и контроль — в `survey-2026-09-16.md`, раздел «Файлы»
  (16 шардов по `0x40`, записи 24 байта, имя `ReadStringU([obj+0x18])`; контроль — 14782 файла,
  пары `count/recLen` 1932/662, 5461/374, 23346/105, 40355/654 без остатка).
  Разблокирует `AreaTransition.WorldArea` → Smart Exit и маршрут кампании.
  **Риск назван в самом survey: `QuestStates` даёт остаток 1340 — без защиты на остаток и на
  диапазон обход уедет в мусор.**
* **`ServerData`: `PlayerInventories 0x72C0 → 0xC9F8`.** По `0x72C0` четыре подряд «больших числа,
  ни на что не похожих», по `0xC9F8` — канонический `NativePtrArray`, и его первый элемент равен
  `PlayerInventories[0].Address` оракула. Оттуда же следует `InventoryHolder.StructSize 0x20 → 0x18`:
  длина массива `0x9F0` делится на `0x18` без остатка (106 держателей) и на `0x20` не делится.
  Плюс сдвиг `+0x140` для полей `ServerInventory`.
  **Не экстраполировать дельту `0x5738` на соседние поля — это одна точка.**
* **`EntityType`: убрать `SmallChest`.** Снимает 27 расхождений `enumdiff` одной строкой.

### 3. Починить сам гейт — он ослеп

`SanityRead` даёт «правдоподобно 45, мусор 2» и **насыщен**: оба «мусора» — паттерны `BasePtr` и
`Loading`, закомментированные в самом вызове и не имеющие ни одного читателя. Выжимать из него
больше нечего, в него надо ДОБАВЛЯТЬ.

Он не проверяет **ни одного поля компонента**, кроме четырёх замеренных, и потому отрапортует
«45 правдоподобно» при любом количестве лжи. Добавить:

* проекцию `LocalPlayer.Pos` — попадает ли она в экран (ловит регресс камеры);
* перепись полей по ПОПУЛЯЦИИ: поле, объявленное в структуре, но константное по всей зоне или
  никогда не похожее на свой тип, — почти наверняка читается не оттуда. Этот приём за один прогон
  нашёл двенадцать поломок без оракула и без владельца.

### 4. Один заход владельца — четыре замера сразу

`ObjectMagicProperties.Rarity` (у эталона `Rarity@0x0`, сразу за ним 24‑байтовый вектор `Mods` —
сильный шаблон поиска; у нас `Rarity@0x7C` не замерен, а от него зависит `CheckRarity`, то есть
**попадание сущности в список вообще**); `Positioned.Reaction` (кандидаты `+0x1E0/+0x1E2/+0x1E3`);
`Shrine`; парные состояния сундука.

### 5. Буферы — это охота, а не подстановка числа

`LifeComponentOffsets.Buffs@0x80` читает четыре нуля подряд, и список возвращается **успешно и
пустым** — то есть молча врёт, а не отказывает. У оракула на том же персонаже 10 живых баффов.
Цена высока и это проверено: элемент `buff[0]` отсутствует в 64 КиБ вокруг компонента, у эталона
структуры `Buffs` нет вовсе, а `get_BuffsList` у него с подменённым телом. Заходить надо от строки
имени баффа обратным поиском по указателю в широком радиусе.

Последствия для плагина крупные (спам флаконами, флакон снятия эффектов не жмётся никогда, ауры
рар‑монстров не видны, цикл перекаста), поэтому пункт не отбрасывается — он просто идёт после
того, у чего числа уже есть.

### 6. UI — последним, и только после камеры

Оракул здесь молчит: `IngameUi = 0` и `UIRoot = 2` при живом HUD. Начинать с парных дампов по
НАВЕДЕНИЮ (2 действия владельца, 2 прогона, 1 диф), а не с «панель открыта / закрыта» — там диф
шумный от аллокаций. Той же парой бесплатно разводится «экран или мир» для `+0x5C0`
(`[IngameState+0x5C0] = (927.9, 1079.1)`, а `+0x5B8` = `(183.6, 1034.1)` — обе пары float).

**Отрицательный исход засчитывается:** если ни один кандидат не проходит контроль по содержимому —
признать, что сломан и `ElementOffsets`, и завести это отдельной задачей.

**`tools/dumpdiff.py` требует правки перед этой веткой:** сейчас он печатает только переходы через
ноль, а нужен и случай «указатель → ДРУГОЙ указатель».

## Ловушки, за которые уже заплачено

1. **Зона меняется между командами.** Любое число без атомарной рамки — угадывание.
2. **`Memory.Read<T>` на мусорном адресе возвращает `default`, а не бросает.** Проверка «не ноль»
   поэтому бесполезна: по незамеренному полю обычно лежит МУСОР, а не ноль. По старому
   `LabDataPtr` было `0x92CFB39000000021`, и код честно строил из него объект, все чтения которого
   молча давали нули. Минимальная проверка — «похоже на канонический указатель»: в
   пользовательской половине адресов и выровнен на 8.
3. **Летучие значения не ищутся поиском.** `EntitiesCount` меняется несколько раз в секунду:
   «НЕ НАЙДЕНО» тут нормальный ответ, а не опровержение поля.
4. **«ok» у `SanityRead` не значит «верно».** Нули проходят проверку диапазона. Живой пример:
   «позиция в сетке (0,0) [ok]» была зелёной ровно до того дня, когда `Positioned` замерили.
5. **Красивая гипотеза проигрывает замеру.** `MapStats` «обязан» был лежать в единственной
   48‑байтной дыре нулей. Он лежит в `0x128`.
6. **Обход по устаревшему указателю ест память** (`ReadHashMap` разогнал процесс до ~4 ГиБ).
   Любой новый обход обязан иметь предел и видимый лог при срабатывании.
7. **Диагностика не должна ронять вызывающего.** `PerformanceTimer.StopAndPrint` уносил
   конструктор `TheGame`; `FilesContainer.FindFile` делал `MessageBox` + `Environment.Exit(1)`.
8. **Тип — тоже гипотеза.** `GridX/GridY` не сходились, пока их читали как float; как int32
   отношение `world/grid` сошлось немедленно. Если критерий не сходится — заподозри ТИП, а не
   смещение.

## Оракул не всеведущ и вдобавок врёт

Пустой ответ эталона **не является** свидетельством об отсутствии объекта: его `LabyrinthData`
в Лабиринте — `null`, `TownPortals` при открытом портале — 0, `IngameUi`/`UIRoot` — 0 при живом HUD.

Хуже: он **ошибается в именах**, и это уже трижды стоило работы.

1. `Chest` и `WorldItem` он называет под общим `nameId 0x1D8` — развела их только vtable.
2. `0x35DFB80` он зовёт `AttributeRequirements` у брони и `Usable` у валюты. Vtable одна, значит
   один из двух ответов неверен, и установить какой — нечем. RVA намеренно НЕ внесён в таблицу:
   неверное имя дало бы ложноположительный `HasComponent`, что хуже отсутствия.
3. `Positioned.Reaction` он читает из байта, отличного от того, где лежит осмысленный enum.
4. `Camera.Position` он читает как M42/M43/M44 собственной матрицы — то есть отдаёт хвост матрицы
   вместо положения камеры в мире. Подтверждено с двух сторон: его `PositionNum` и его же
   `Snapshot` печатают одни и те же три float.
5. `Camera.ZFar` у него на этом клиенте — элемент M12/M22 ЧУЖОГО матричного блока (`0.5886619`),
   как дистанция не осмысленный ни в каком виде. `ZNear` у него нет вовсе.

И отдельно — про то, откуда у оракула вообще брать форму: **метаданные его `GameOffsets.dll`
подделаны защитой**, ровно как и тела методов. Раскладка камеры в файле объявляет `Position`
РАНЬШЕ матрицы, а живьём он читает её ПОЗЖЕ на `0x34`; ни при каком базовом адресе это не
совместимо. `Marshal.OffsetOf` в том же процессе, где код эталона уже отработал верно, возвращает
ту же подделку. Значит форму структур у него можно брать только ПОВЕДЕНЧЕСКИ — вызовом, — а не
чтением метаданных, и `RefOffset --layout` для камеры бесполезен.

Поэтому: соединение с оракулом делай **по адресу**, а не по имени и не по `nameId`; и если оракул
сам себе противоречит — это результат, который надо записать, а не расхождение, которое надо
замять.

## Чего НЕ делать

1. **Копировать числа из `RefOffset --layout` / `ForkProbe --layout`.** Доказано трижды:
   эталонный `IngameDataOffsets` даёт `0x20/0xA0/0xA8/0xB0/0xD0` при уже закрытых истинных
   `0xB0/0x968/0x970/0xA28/0xC08`, и разность НЕПОСТОЯННА — это не сдвиг. Оттуда берётся форма
   (набор и порядок полей), и только она.
2. **Разводить `LocalPlayer` `+0x970` против `+0x10E8` отдельной работой.** `+0x10E8` опознан:
   поле `+0x30` подобъекта с собственной vtable по `Data+0x10B8`.
3. **`TownPortals`.** Дважды закрыто отрицательно в первых `0x10000` байт `IngameData`; у эталона
   поля нет вовсе. Если делать — искать в `ServerData` и только попутно с UI‑серией.
4. **Гнаться за `parity.sh`.** 475 незакрытых из 753 — это в основном типы и члены, которых
   плагин не касается. Гейт полезен как сторож регресса, но как цель он ложный: его можно сильно
   сдвинуть, не сделав плагину ничего.
5. **Компонент `Pathfinding` целиком.** Единственный потребитель — диагностический перечень;
   `IsMoving` плагин берёт из своей модели движения.

## Правила работы

- Пушить сразу в `master` (PoeAPI) и в `main` (MovementHelperPoe). Веток и PR не создавать.
- Обсуждение, коммиты и документы — по‑русски. **Код и комментарии в `Core/` и `GameOffsets/` —
  по‑английски.** В `tools/` язык смешанный: смотри на соседний файл.
- Числа — только замеренные. «Должно быть так» — гипотеза, и помечается как гипотеза.
- Каждое утверждение в коммите — с указанием, чем установлено.
- Инструмент, которым снят замер, обязан лежать в репозитории: замер, который нельзя повторить,
  слабее замера, который можно.
