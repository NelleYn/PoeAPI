## Сущность — самое важное

Наш `EntityListOffsets {FirstAddr 0x0, SecondAddr 0x10, Entity 0x28}` **ВЕРЕН**, не трогать:
подтверждено дампом узла — у потомка головы списка по `+0x28` лежит адрес, по которому та же
vtable (`PathOfExile_KG.exe+0x3456508`), что в `+0x0` у трёх заведомо настоящих сущностей.

Истинная раскладка сущности, совпала поштучно на трёх сущностях (игрок, дудад, пет):

| смещение | что | как подтверждено |
|---|---|---|
| `+0x00` | vtable, одна и та же у всех | `+0x3456508` |
| `+0x08` | `EntityDetails*` | у игрока `0x5F522251CA0`, эталон печатает `MainObject` = то же число |
| `+0x10/+0x18/+0x20` | `StdVector` массива указателей на компоненты | у игрока 12 указателей, поштучно совпали с адресами компонентов эталона и в том же порядке |
| `+0x28` | вторая vtable (`+0x34564D0`) | |
| `+0x30/+0x38/+0x40` | второй вектор, ровно `0x58` байт у ВСЕХ сущностей | к компонентам отношения не имеет |
| `+0x70` | `uint InventoryId` | игрок `0x500`, пет `0x500`, дудад 0 — совпало с эталоном трижды |
| `+0x78` | `IngameData*` | `0x5F55990D800` у всех трёх |
| `+0x88` | `uint Id` | `0x1AB` / `0xC0000102` / `0x1AC` — совпало с эталоном трижды |
| `+0x8C` | `Flags` | эталон даёт 12 у всех трёх, низкий БАЙТ равен `0x0C` у всех трёх, верхние три байта разные → **читать байтом, ширина не доказана** |
| `+0x98` | прямой указатель на `Positioned`, минуя таблицу | равен `CacheComp[0]` эталона на всех трёх |

> Строка `+0x70` **опровергнута** замером того же дня на сорока сущностях — см. врезку выше и
> [entities-measured.md](entities-measured.md). Остальные строки этой таблицы подтверждены.

**Что у нас сломано и почему — обе причины найдены:**

1. `PathEntityOffsets` сдвинут на `-0x8`. Строка пути лежит по `details+0x08`, длина по
   `details+0x18`, а мы читаем `+0x10` и `+0x20`. Критерий проверки железный: число по `+0x18`
   равно длине строки по `+0x08` — 33 для `Metadata/Characters/DexInt/DexInt`, 46 для
   `Metadata/MiscellaneousObjects/DoodadNoBlocking`, 44 для `Metadata/Pet/ScientistLabRat/...`.
   Из-за нуля в `Path.Ptr` сущность получает `IsValid=false` и `EntityType.Error` — умирает вся
   классификация.
2. `Entity.cs:377` читает `_componentLookup = M.Read<long>(Address + 0x8, 0x38, 0x30)`. Второе
   звено мертво: `[details+0x38]` = `0x0000000200000007`, память по нему не отображена. Живой
   корень таблицы — `[details+0x28]` (у трёх сущностей разные адреса, но одна vtable `+0x35ABE08`).

**Модель поиска компонента по имени ДРУГАЯ.** `NativeListNodeComponent {Next, Prev, String,
ComponentList}` на клиенте больше нет — ни связного списка, ни указателей на строки. Вместо него
открытая хеш‑таблица фиксированных слотов по 8 байт: `{uint32 nameId; uint32 индекс в массиве
компонентов}`, пустой слот — ноль. Слотов степень двойки: 16 у игрока (12 компонентов), 16 у пета
(10), 8 у дудада (4). Таблица лежит не в сущности, а в общем на метаданные `EntityDetails`.

Путь целиком: `details = [ent+0x08]`, `lookup = [details+0x28]`, `slots = lookup+0x40` (StdVector),
адрес компонента `= [comps.First + index*8]`.

**`nameId` — не хеш строки, а маленький глобальный номер типа**, одинаковый у разных сущностей.
**Строк имён компонентов в памяти клиента НЕТ ВООБЩЕ**, поэтому таблицу «тип C# → nameId» придётся
собирать и хранить. Двенадцать пар уже сняты:

    Render 0x101   BaseEvents 0x114   Positioned 0x11C   Animated 0x151
    Life   0x15F   Player     0x186   Pathfinding 0x18F  Stats     0x1A7
    Actor  0x1C6   Buffs      0x24B   PlayerClass 0x274  PetAi     0x2AD

Добрать: `Base`, `WorldItem`, `Mods`, `RenderItem`, `Quality`, `Stack`, `ObjectMagicProperties`,
`Chest`, `AreaTransition`, `Shrine`. Запасной ключ, если `nameId` поедет между патчами, — vtable
дескриптора из `lookup+0x10`, она устойчива по типу.

> Оба абзаца выше про `nameId` **опровергнуты** замером того же дня: `nameId` не однозначен ни в
> одну сторону, и таблица из двенадцати пар ключом быть не может. Что осталось верным — «строк
> имён компонентов в памяти нет» и «таблицу придётся хранить у себя»; хранить надо пары
> «тип → RVA vtable компонента». См. врезку выше и [entities-measured.md](entities-measured.md).
>
> Важно для истории: таблица «тип C# → `nameId`» так и осталась **предложением этого документа** —
> в код она не вносилась никогда, отдельного файла под неё в репозитории не существовало. Замер
> опроверг её до того, как она стала кодом. Из кода замер вытеснил другое — обход
> `NativeListNodeComponent` (абзац выше), чей файл этим изменением удалён.
>
> Две из пяти известных теперь коллизий — `Positioned 0x11C/0x21C` и `Life 0x15F/0x25F` — бьют прямо
> по строкам таблицы выше: в ней `Positioned 0x11C` и `Life 0x15F`, то есть только «нижняя» форма.

`ObjectHeaderOffsets` у нас фикция: `ComponentList@0x40` читает `0x8600000000010000` у игрока и
ноль у второй сущности. Сжать до `{vtable@0x0, MainObject@0x8}`.

## Файлы

Реестр лежит по `[fileRoot+0x00]`, **не** `+0x08`: массив 16 шардов по `0x40`, записи по 24 байта,
`obj` на `+16`, имя — `ReadStringU([obj+0x18])`. `NumberOfRecords = (LastArrItem-FirstArrItem)/24`,
`RecordLength = (LastRecord-FirstRecord)/count` — **с обязательной защитой на остаток и диапазон**:
`QuestStates` даёт остаток 1340 и без защиты уедет в мусор.

Контрольные числа: всего файлов 14782; пары `count/recLen` — 1932/662, 5461/374, 23346/105,
40355/654 без остатка.

## Три бесплатные починки, не требующие замера

1. `CurLatency` ← `ServerData.Latency`. Сейчас 0 вместо 25, и это **молча меняет частоту
   перечитывания памяти во всём движке**.
2. Убрать `MessageBox` + `Environment.Exit(1)` из `FilesContainer.FindFile` — диагностика не
   должна ронять хост (правило уже было нарушено `PerformanceTimer`, см. README).
3. Поправить ложный комментарий у `IngameDataOffsets.LocalPlayer`: `+0x10E8` — не «unrelated run of
   floats and counters», а поле `+0x30` подобъекта с собственной vtable по `Data+0x10B8`, которому
   принадлежит и `EnvironmentData`.

## Чего обследование НЕ подтвердило

`PositionedComponentOffsets` эталона не ложится на память ни при какой базе; числа из
`RefOffset --layout` / `ForkProbe --layout` непереносимы и здесь тоже — проверено на
`IngameDataOffsets`, где эталон даёт `0x20/0xA0/0xA8/0xB0/0xD0` при уже закрытых истинных
`0xB0/0x968/0x970/0xA28/0xC08`, причём разность непостоянна, то есть это не сдвиг.
`HashComponents` у эталона пуст на всех трёх сущностях — мёртвое поле, переносить незачем.
`RefOffset` вообще не знает типа `IngameStateOffsets`.
