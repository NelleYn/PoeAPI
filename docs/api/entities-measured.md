# Слой сущностей — замерено 2026‑09‑16 на живом клиенте

> Клиент `PathOfExile_KG` pid 13660, база модуля `0x7FF78FCD0000`, зона «The Reliquary» `1_5_7`
> (акт 5, ур. 44, хэш `0x57BE9BD9`), 132–142 сущности. Персонаж — Shadow с Chaos Inoculation.
>
> Основной массив чисел снят в этой зоне. Позже в тот же день добавились ещё три захода —
> **брошенные вещи, бой, город**, — при **той же базе модуля**; ими закрыты предметные компоненты,
> `Portal`/`NPC`/`DiesAfterTime` и путь к предметной сущности. Где число пришло из позднего захода,
> это сказано прямо в его абзаце.
>
> Все числа сняты **атомарно**: цепочка `IngameState → Data → EntityList → сущность → details →
> lookup → компоненты` прочитана В ОДНОМ процессе, и каждый снимок обрамлён проверкой «зона и база
> `Data` не менялись». Снимки с признаком смены состояния отброшены.
>
> Почему рамка обязательна: первая попытка мерить теми же командами по отдельности дала дамп
> `Data+0xA28`, целиком состоящий из float'ов, — между двумя командами игрок сменил зону, и `Data`
> переехал.
>
> **Долг воспроизводимости закрыт: инструмент внесён в репозиторий — `tools/EntCap`.** Снимки
> делались им, и он повторяет любой из них одной командой:
>
>     dotnet build -c Release tools/EntCap/EntCap.csproj
>     FindOffset.exe --ingame-state                     # адрес IngameState
>     EntCap.exe --igs <адрес> --byvtbl                 # разбор по vtable и контроль ent+0x98
>     EntCap.exe --igs <адрес> --comp                   # Positioned / Render / Life с критериями
>     EntCap.exe --igs <адрес> --items                  # спуск в предметную сущность
>     EntCap.exe --igs <адрес> --watch 90               # накопление за время: снаряды, эффекты
>
> Он намеренно НЕ ссылается на `GameOffsets`, в отличие от `FindOffset` и `SanityRead`. Те обязаны
> читать именно нашими оффсетами, потому что проверяют их; этот — наоборот, должен уметь читать
> гипотезу, которой в коде ещё нет. Плата за это — таблица vtable в нём является снимком и
> синхронизируется руками; расхождение видно как «не в таблице N» там, где код опознаёт всё.
>
> **Исключение — таблица «тип компонента → RVA vtable».** Её опорный инструмент в репозитории:
> `RefLive --harvest`, научен печатать RVA рядом с именем. Соединение при этом **поадресное**:
> слева имя из `CacheComp` оракула, справа vtable, прочитанная своим кодом по `[компонент+0x00]`,
> ключ соединения — адрес компонента. Ни имена-строки, ни `nameId` в соединении не участвуют.
> Таблица в её нынешнем виде собрана **четырьмя заходами одного дня**: зона «The Reliquary»,
> брошенные вещи, бой, город. Одной командой, как прежде говорилось здесь, она уже не снимается —
> одна команда даёт то, что видно из текущей зоны, а не всю таблицу.
> Проверка после внесения: в городе — зоне, в которой таблица не снималась, — `--byvtbl`
> опознал ВСЕ компоненты у 40 сущностей из 40 при нуле неизвестных, и контроль
> «`Positioned` по vtable совпадает с прямым указателем `ent+0x98`» сошёлся на всех 40.

Документ разделён намеренно: **что подтверждено содержимым**, **что опровергнуто**, **что сужено,
но НЕ закрыто**, **что осталось незакрытым** и **что для этого должен сделать владелец в игре**.
Второе важнее первого — опровергнуто ровно то, на чём уже стоит код. Третье — граница между ними:
там лежат числа, по которым замер продвинулся, но не дошёл до утверждения, и выдавать их за
замеренные нельзя.

## Что подтверждено содержимым

### Раскладка сущности

| смещение | поле | чем подтверждено |
|---|---|---|
| `+0x08` | `EntityDetails*` | по нему читается путь, критерий длины сошёлся **141 из 141** |
| `+0x10/+0x18/+0x20` | `StdVector` указателей на компоненты | `(Last−First)/8` равно числу непустых слотов таблицы у **каждой** сущности: 4=4, 9=9, 13=13, 14=14 |
| `+0x70` | **НЕ `InventoryId`** | см. «Что опровергнуто» |
| `+0x78` | `IngameData*` | равен текущему `Data` у всех сущностей выборки |
| `+0x88` | `uint Id` | лежит в одном qword с `Flags` — например `0x0000260C_000004CE` |
| `+0x8C` | `Flags`, читается байтом | младший байт `0x0C` у **40 из 40**; старшие байты различаются, но правило НЕ установлено — см. «[Старшие байты `Flags`](#старшие-байты-flags--правило-не-установлено)» |
| `+0x98` | прямой указатель на `Positioned` | совпал с компонентом, опознанным по vtable, **50 из 50** |

Про `+0x00` (vtable самой сущности) сегодняшний замер ничего не говорит: значение
`PathOfExile_KG.exe+0x3456508` — из обследования [survey-2026‑09‑16](survey-2026-09-16.md),
три сущности, **не переподтверждено**.

### Путь метаданных — `PathEntityOffsets`

`Path` по `details+0x08`, `Length` по `details+0x18`.

Критерий железный и проверен на всей зоне: число по `details+0x18` равно **фактической длине**
строки по `details+0x08`, и строка начинается с `Metadata/`. Сошлось **141 из 141**.
Примеры: `Metadata/MiscellaneousObjects/Doodad` = 36, `Metadata/Chests/DarkPot2v2` = 26,
`Metadata/Monsters/OriathCivilian/OriathCivilianGhostFemaleRanged1@44` = 68.

Цена старого бага: из-за нуля в `Path.Ptr` сущность получала `IsValid=false` и `EntityType.Error`,
то есть умирала вся классификация.

### Слот-таблица — устройство подтверждено, назначение НЕТ

Путь `details → [+0x28] = lookup → [+0x40] = StdVector слотов`, слот — 8 байт
`{uint32 nameId, uint32 index}`, пустой слот — ноль, адрес компонента `= [comps.First + index*8]`.

Подтверждено дважды и независимо:

* число **непустых слотов равно числу компонентов** в векторе у каждой разобранной сущности
  (4=4, 9=9, 13=13, 14=14);
* у **каждого** разрешённого компонента `[компонент+0x08]` равен адресу своей сущности.

Размер таблицы — степень двойки: встретились 8, 16 и 32.

Устройство — это не назначение. Что означает `nameId` в слоте, замер НЕ установил; установлено
только, чем он **не** является (следующий раздел).

### Тип компонента опознаётся по его собственной vtable

`[компонент+0x00]`, приведённая к RVA (минус база модуля `0x7FF78FCD0000`), уникальна в обе
стороны: 20 разных `nameId` дали 19 разных vtable, и обе коллизии `nameId` объяснились точно —
`0x114`/`0x214` → одна vtable, `0x12E`/`0x22E` → одна vtable, а `0x1D8` → **две** vtable.
Добор того же дня дал **третий** случай «два `nameId` — одна vtable»: `0x156` и `0x256` ведут на
одну и ту же vtable `0x35DA8B8` (`StateMachine`). Разница снова ровно `0x100`. Заход в бою поднял
ещё четыре таких коллизии разом, среди них — компоненты горячего пути; подробности и цена —
в разделе «[`nameId` — не идентификатор типа компонента](#nameid--не-идентификатор-типа-компонента)».

Таблица «тип → RVA vtable», **замерено 40 пар**: 30 для сущностей зоны, 9 для предметных
компонентов и одна — `Projectile` — установленная заметно слабее остальных (см. ниже).

Пометки «только у брони / только у оружия / у всех предметов» — это то, на чём компонент

Имена в левом столбце — не наше предположение: их дал оракул (`RefLive --harvest`, его `CacheComp`).

**Как снята эта таблица.** Соединение — **поадресное**: слева имя из `CacheComp` оракула
(`RefLive --harvest`, научен печатать RVA рядом с именем), справа vtable, прочитанная своим кодом
по `[компонент+0x00]`; ключом соединения служит **адрес компонента**, а не имя-строка и не `nameId`.
Четыре захода одного дня: зона «The Reliquary», брошенные вещи, бой, город. У **каждого** имени
ровно **один** RVA: ни одной неоднозначности «имя → две vtable» нет. Все двенадцать имён, которые
называло [обследование](survey-2026-09-16.md) (`Render`, `BaseEvents`, `Positioned`, `Animated`,
`Life`, `Player`, `Pathfinding`, `Stats`, `Actor`, `Buffs`, `PlayerClass`, `PetAi`), сошлись
**12 из 12** в трёх прогонах из четырёх; в одном `BaseEvents` прочитался как `0x214` — это ровно
та коллизия `nameId`, о которой ниже, а не расхождение vtable. За четыре прогона ни одна пара
в таблице не дрогнула, `DiesAfterTime` вышел идентично дважды.

Куда эти числа идут в коде: `GameOffsets/ComponentVtables.cs`, массив `MeasuredPairs` — там же
рядом лежит список ещё не замеренных типов. Если в коде пар меньше сорока, значит новые просто ещё
не внесены; на сам замер это не влияет, но типы, которых нет в массиве, движок не опознаёт.

**Пятнадцать пар — новые** против прежней таблицы из двадцати пяти: `Brackets`, `DiesAfterTime`,
`Functions`, `NPC`, `Portal` (сущности зоны) и все девять предметных плюс `Projectile`.

Это прямо закрывает замечание рецензента о недостижимых `EntityType.AreaTransition` / `Waypoint` /
`IngameIcon`, и закрывает его сильнее, чем три строки: в `Entity.ParseType` **весь** этот блок
классификации стоит за одним условием `HasComponent<MinimapIcon>()`, а внутри него `AreaTransition`
решается компонентом, `Waypoint` — окончанием пути. Пока `MinimapIcon` был вне таблицы, ни одна
ветка внутри не могла выполниться **вообще**, включая `IngameIcon` — ветку по умолчанию. Тем же
добором становится достижим `EntityType.HideoutDecoration` (по `HideoutDoodad`), а городским
заходом — `TownPortal` и `Portal` (по `Portal`) и `Npc` (по `NPC`). Что внутри этого блока
по-прежнему недостижимо: `Monolith` — его vtable не замерена. Вне блока так же недостижим
`Shrine`: зоны со святилищем в заходах не было.

Чего эта таблица **не** говорит: она не говорит ничего о **полях** перечисленных компонентов.
Замерена только vtable, то есть право ответить «компонент такого типа здесь есть». Смещения внутри
`AreaTransition`, `MinimapIcon`, `StateMachine`, `TriggerableBlockage`, `HideoutDoodad`, `PetAi`,
`Portal`, `NPC`, `DiesAfterTime`, `Brackets`, `Functions` и всех девяти предметных компонентов
перенесены из эталона (а у части типов в форке и класса-то нет) и этим замером не проверялись.
Классов `Brackets`, `Functions`, `LocalStats` и `Projectile` в `Core/PoEMemory/Components/` нет
вовсе: их vtable замерены, спрашивать их пока некому.

**Контроль модели, 50 сущностей семи видов:**

* `Positioned`, найденный по vtable, совпал с прямым указателем `ent+0x98` — **50 из 50**;
* все компоненты опознаны у **49 из 50** сущностей (у одной один компонент вне таблицы);
* состав совпал с тем, что печатает оракул: у игрока ровно 12 компонентов, у монстра 13,
  у сундука 9, у дудада 4.

Модель по vtable **не нуждается в слот-таблице вовсе**: достаточно пройти вектор компонентов
сущности и сверить vtable каждого. Это короче разбора хеш-таблицы и, в отличие от него, опирается
на замеренный ключ.

### Предметная сущность — свой путь и своя vtable

Предметные компоненты не появляются на наземной сущности ни при каком обходе: дроп — это
сущность-контейнер с компонентом `WorldItem`, а сам предмет — **вторая сущность**.

**Путь к ней ЗАМЕРЕН: `WorldItem + 0x28`**, совпало **14 из 14** на той же выборке брошенных вещей.
Подтверждение формой: шаг между соседними компонентами `WorldItem` равен `0xD0`, поэтому то же поле
повторно находится по `+0xF8` и `+0x1C8` — это соседние компоненты, а не другие поля той же
структуры.

`Core/PoEMemory/Components/WorldItem.cs` читает `Address + 0x28` **давно** — число унаследовано от
апстрима. Изменилось не число, а его статус: теперь оно **замерено**, а не принято на веру. Код
менять не нужно; нужен был провенанс, и это он.

У предметной сущности **своя vtable, RVA `0x35E0358`**, отличная от наземной `0x3456508`. Именно
поэтому поиск «по vtable сущности» предметные сущности не находил: он искал наземное значение.

### `Projectile` — установлен слабее всех остальных пар

    Projectile            0x35A0D10

Помечать в коде явно. Оракул **живым снарядом не застал** — три попытки за один бой. Имя приклеено
двумя косвенными доводами: `nameId 0x1CA`, который оракул называл в другом прогоне, и корреляция —
этот vtable встречается **только** на `Metadata/Projectiles/ImpactingSteelProjectile` и
`...Secondary`. Ни один из двух доводов не является поадресным соединением, на котором стоят
остальные 39 пар, поэтому пара помечена **слабой** здесь и должна быть так же помечена там, где
она войдёт в `GameOffsets/ComponentVtables.cs`.

Наблюдение, ограничивающее масштаб неизвестного: **1609 проходов, 284312 просмотров сущностей,
неопознанных vtable ровно четыре.**

### НЕ ВНОСИТЬ: `0x35DFB80` — неразрешённая коллизия и ВТОРАЯ ошибка самого оракула

`0x35DFB80` оракул называет `AttributeRequirements` у брони и оружия, но `Usable` у валюты.
Соединение поадресное, экземпляры компонентов разные, vtable одна — **а vtable есть тип**, значит
одно из двух имён неверно, и какое именно, установить нечем.

Пара **не внесена**. В нашем форке класса `Usable` нет вовсе (`Core/PoEMemory/Components/` содержит
`AttributeRequirements.cs` и не содержит `Usable.cs`), поэтому пропуск не стоит ничего, а неверное
имя дало бы **ложноположительный** `HasComponent` — ровно ту болезнь, от которой уходили с `nameId`.

Это **второй** случай ошибки самого оракула. Первый — `Chest` и `WorldItem` под общим `nameId
0x1D8`; там их развела как раз vtable. Здесь vtable развести не может, потому что она одна.

**Без имени:** `0x35A5C68` (`nameId 0x11E`) на `Metadata/Effects/Effect` — оракул не назвал.
Компонент такого типа существует и встречается; как он называется, замером не установлено.

### Компоненты горячего пути

| компонент | поле | смещение | чем подтверждено |
|---|---|---|---|
| `Positioned` | `GridX`/`GridY` | `0x294`/`0x298`, **int32** | `world/grid = 10.87` по обеим осям у каждой сущности |
| `Positioned` | `WorldPosition` | `0x2B8`, 3 float | по X и Y ТОЧНО совпадает с `Render.Pos` |
| `Render` | `Pos` | `0x120`, 3 float | равен `Positioned.WorldPosition` по X и Y |
| `Render` | `Bounds` | `0x12C`, 3 float | собственного критерия НЕТ: три float вплотную за `Pos` |
| `Render` | `Name` | `0x148`, длина `0x158`, ёмкость `0x160` | длина строки равна полю длины на строках обеих форм |
| `Life` | HP max/cur | `0x1A4`/`0x1A8`, голова блока `0x180` | значения совпали с фактом вне памяти, см. ниже |
| `Life` | мана max/cur | `0x1F4`/`0x1F8`, голова блока `0x1D0` | там же |
| `Life` | ES max/cur | `0x23C`/`0x240`, голова блока `0x218` | там же |

`GridX/GridY` — **int32, не float**. Первая проба дала «критерий не сошёлся» именно потому, что
делила на float-прочтение; как int отношение `world/grid` сходится немедленно:
`4114.13/378 = 10.884`, `11005.44/1012 = 10.875`, `4984.34/458 = 10.883`, `5896.74/542 = 10.879`.

`Render.Name` — встроенный `NativeUtf16Text`: короткая строка лежит прямо в объекте, длинная — по
указателю в тех же байтах, и различаются они по полю ёмкости (`>= 8` — куча). Правило проверено на
строках обеих форм: «Risen Saint» (11), «Gold Pot» (8), «Reliquarian» (11), «Shadow» (6), «» (0).

`Life` — три блока, и **голова каждого содержит указатель НА САМ компонент**; это и есть примета,
по которой блок опознаётся, и она сошлась у всех разобранных. Порядок блоков в памяти — здоровье,
мана, щит.

**Самое сильное подтверждение здесь — не отношение и не указатель, а внешний факт.** У персонажа
Chaos Inoculation, и блоки по этим смещениям дают **HP 1/1, мана 1135/67, ES 10353/10353**.
Это совпадение с тем, что известно о персонаже ВНЕ памяти, — свидетельство, которого нельзя
получить подгонкой смещений.

**Про мановые числа — ровно то, что прочитано, и ни словом больше.** `1135/67` — это один снимок;
**более поздний замер в той же сессии дал `1135/1135`**. Оба числа — замеры, а вот причина, по
которой в первом снимке текущая мана была низкой, **не замерена**: трата, реген и зарезервированный
пул дают одну и ту же пару чисел, а поля, которое их различает, в компоненте не найдено. Прежняя
редакция комментариев в `GameOffsets/LifeComponentOffsets.cs` и `Core/PoEMemory/Components/Life.cs`
объясняла `67` аурами и «шаром маны намного выше» как установленным фактом — **это снято**: замер
того же дня такому объяснению скорее противоречит. Любое объяснение `67` — **гипотеза**; довод в
пользу `NaN` у `MPPercentage` в нём не нуждается и на нём не стоял.

### Побочно: `ServerData.Latency` = `+0xC490`

Замерено в том же заходе, к слою сущностей отношения не имеет. Оракул в этот момент говорит
`Latency = 3`; по `[Address+0xC490]` лежит `0x000004AA00000003`, младший uint32 — ровно `3`.
Число, которое оно заменило, — `0x6CA0` — даёт там `0x128CBA26`, что не является задержкой ни при
каком прочтении.

## Что ОПРОВЕРГНУТО

Оба утверждения — из обследования [survey-2026‑09‑16](survey-2026-09-16.md). Это главный результат
замера. **Но статус у них был разный, и прежняя редакция этого абзаца путала два разных положения
дел; ниже — как было на самом деле.**

* **`nameId` как ключ типа был ПРЕДЛОЖЕНИЕМ, а не закоммиченной таблицей.** Обследование
  предлагало собрать и хранить таблицу «тип C# → `nameId`» и приводило двенадцать пар прямо в
  тексте [survey-2026-09-16.md](survey-2026-09-16.md). В коде такой таблицы **никогда не было**:
  файла `GameOffsets/ComponentNameIds.cs` нет ни в рабочем дереве, ни в истории репозитория —
  `git log --all -S ComponentNameIds` не находит ни одного коммита. Поэтому фраза «таблицы
  `ComponentNameIds.cs` больше нет», стоявшая здесь раньше, **неверна**: нечему было исчезать.
  Замер опроверг предложение до того, как оно попало в код, — и это, кстати, дешевле, чем наоборот.
* **Что замер действительно вытеснил ИЗ КОДА** — обход `NativeListNodeComponent`: связный список
  узлов `{Next, Prev, String, ComponentList}`, по которому форк искал компонент по имени-строке.
  Такого списка на клиенте нет, файл `GameOffsets/Native/NativeListNodeComponent.cs` этим
  изменением **удалён**, и его место занял разбор по vtable (`GameOffsets/ComponentVtables.cs`,
  устройство слот-таблицы — `GameOffsets/ComponentLookupOffsets.cs`).
* **`EntityOffsets.InventoryId` в коде стоял** — и остался на месте, но рядом с ним теперь
  константа `InventoryIdMeasured = false`: число не удалено, но и не выдаётся за замеренное.

### `nameId` — не идентификатор типа компонента

Обследование утверждало: «`nameId` — маленький глобальный номер типа, одинаковый у разных
сущностей». **Это неверно, и неверно в обе стороны.**

* Один тип — разные `nameId`, **пять разных имён**: `BaseEvents` лежит под `0x214`
  у `Metadata/Chests`, но под `0x114` у дудадов, монстров и Terrain; `InteractionAction` —
  `0x22E` у сундуков против `0x12E` у остальных; `StateMachine` — `0x156` и `0x256`, обе ведут
  на одну vtable `0x35DA8B8`; и, из боевого захода, `Positioned` — `0x11C`/`0x21C` и `Life` —
  `0x15F`/`0x25F`. Разница ровно `0x100` во всех пяти.
* Один `nameId` — разные типы: под `0x1D8` живут `Chest` (у `Metadata/Chests`) и `WorldItem`
  (у `Metadata/MiscellaneousObjects/WorldItem`).

**Новое доказательство, и оно дороже прежних.** Один прогон оракула в бою поднял **четыре**
коллизии «одно имя — разные `nameId`» сразу, все с шагом ровно `+0x100`:

    BaseEvents  0x114/0x214       Positioned         0x11C/0x21C
    Life        0x15F/0x25F       InteractionAction  0x12E/0x22E

Два имени здесь уже были известны, два — `Positioned` и `Life` — новые. Особая цена именно у них:
это **компоненты горячего пути**, и раньше они встречались только в «нижней» форме (`0x11C`,
`0x15F`). На модели `nameId` это значит, что поиск позиции и здоровья у части сущностей **молча не
находил бы ничего** — не падал бы, не логировал, а возвращал «компонента нет» у сущности, у которой
он есть. Таблица vtable за четыре прогона при этом не дрогнула.

**Чем эти два типа всё-таки различены — замером, а не рассуждением.** `nameId 0x1D8` у `Chest`
и `WorldItem` общий, но vtable разные и встречаются они на непересекающихся множествах сущностей:
`0x3465EC0` (`Chest`) встретился **только** на `Metadata/Chests/*` — **7 сущностей**, `0x3465DA8`
(`WorldItem`) — **только** на `Metadata/MiscellaneousObjects/WorldItem`. То есть vtable отделяет
ровно ту пару, на которой `nameId` молча отдал бы чужой компонент.

Все случаи установлены одинаково — соединением двух источников по **адресу компонента**: имена —
у оракула (`RefLive --harvest`, его `CacheComp`), `nameId` и vtable — своим чтением. Оракул сам
поднял флаг: «ОДНО ИМЯ — РАЗНЫЕ nameId в одном запуске» — сперва на `BaseEvents` и
`InteractionAction`, затем на `StateMachine` в доборе того же дня и на всех четырёх сразу в бою.

Почему это опровержение, а не уточнение: на том утверждении стояла бы статическая таблица
«тип C# → `nameId`» — та, которую предлагало обследование и которая в код так и не попала. Ключ,
не однозначный ни в одну сторону, даёт не «иногда не находит», а **два разных отказа сразу**:
молча чужой компонент (`WorldItem` вместо `Chest`) и молча «ничего нет» там, где компонент есть
(`Positioned`, `Life` в верхней форме). Чем заменяется — vtable самого компонента, см. выше.

Запасной ключ, который обследование предлагало на случай, если `nameId` поедет между патчами —
vtable дескриптора из `lookup+0x10`, — этим замером не проверялся. Сработала vtable **самого
компонента**, а не дескриптора.

### `InventoryId +0x70` — НЕ подтверждён

Обследование сверяло его на трёх сущностях. На сорока он ломается: у `Metadata/Chests/DarkPot2v2`
по `+0x70` лежит **указатель в модуль игры** `0x00007FF792EFFF00`, и чтение его как `uint32` даёт
`0x92EFFF00` — просто младшую половину указателя. У других сущностей там `0`, `0x100`, `0x400`,
а также `0x6050100`, `0x9D690300`, `0x459FD100`, `0x5050500`, `0x1010100`.

Согласия на трёх сущностях недостаточно — ровно как «единственность есть свойство окна, а не поля».
Настоящее поле не найдено; поле оставлено незакрытым.

## Сужено, но НЕ закрыто

Этот раздел — про два числа, по которым замер продвинулся, но НЕ дошёл до утверждения. Оба
остаются в коде в прежнем виде: кандидат — не замер, и выдавать его за замер нельзя.

### `Reaction` — сужен до трёх байт одного qword

Что есть:

* **Оракул** в этот момент говорит: `Reaction` = **1** у игрока, **0** у монстра. Это всё, что он
  даёт, — две точки.
* В сыром дампе `Positioned` этим двум точкам отвечают **ровно два байта**: `+0x1E0` и `+0x1E2`.
  У обоих поведение одинаковое: игрок 1, пет 1, все **13** монстров 0. Разделить их между собой
  нечем — на этой выборке они неразличимы.
* Рядом, в том же qword, лежит байт `+0x1E3` с более богатым набором значений: игрок 1, пет 1,
  монстры 2, сундуки и предметы 3, Terrain 3, `AreaTransition` и вэйпоинт 5, эффекты 255,
  дудады 1.

Почему выбрать нельзя:

* `+0x1E0`/`+0x1E2` ведут себя как **булев признак враждебности**, `+0x1E3` — как **номер
  фракции**. Отделяет одно от другого ровно один случай — **союзный монстр**: у него «враждебность»
  и «фракция» обязаны разойтись. В зоне «The Reliquary» союзного монстра не было, и поздние заходы
  того же дня — вещи, бой, город — его тоже не принесли, поэтому такого случая в выборке нет
  вообще. Это единственная строка, которую четыре захода **не** сдвинули ни на шаг.
* Сверить с эталоном нельзя: `PositionedComponentOffsets` эталона **документировано не ложится**
  на эту сборку (см. [обследование](survey-2026-09-16.md), раздел «Чего обследование НЕ
  подтвердило»; остальная часть структуры уехала примерно на `0x1B0` байт). Значит, согласие
  эталонного числа с любым из трёх кандидатов — слабый довод, а не подтверждение.

**Вывод: не применять.** В `GameOffsets/PositionedComponentOffsets.cs` `Reaction` остаётся на
унаследованном `0x58` с константой `ReactionMeasured = false`; `Entity.IsHostile` стоит на этом же
числе и остаётся незамеренным. Записано здесь сужение — «искать в qword по `+0x1E0`, кандидатов
три», — а не решение.

### Старшие байты `Flags` — правило НЕ установлено

Замерено ровно одно: **младший байт `Flags` равен `0x0C` у 40 из 40** сущностей. Пример qword,
общего с `Id`: `0x0000260C_000004CE`.

Про старшие байты замер говорит только то, что они **различаются**. Прежняя формулировка
«дудады `0x00` / монстры `0x26` / сундуки `0x22`» — **неверна**, и опровергнута она собственными
числами того же дня:

* монстры дают **и** `0x26`, **и** `0x22` — `Metadata/Monsters/ReliquaryMonsterEmerge` читается
  как `0x0000220C`;
* сундуки дают и `0x0000220C`, и `0xFFFF220C`.

То есть группировки «по виду сущности» нет: одна и та же категория попадает в разные группы, а
разные категории — в одну. По какому правилу меняются старшие байты — **не установлено**. Пока
правила нет, поле читается байтом; читать шире — значит втащить в замеренное число незамеренный
смысл.

## Что осталось незакрытым

1. **`InventoryId`** — старое число опровергнуто, нового нет. Разрешать его разумно оракулом
   (`RefLive --as Entity <адрес>` даёт истинное значение, от которого можно искать), а не выборкой:
   выборка уже один раз согласилась на трёх сущностях и ошиблась.
2. **Ширина `Flags`.** Замерен только младший байт (`0x0C` у 40 из 40). Старшие байты различаются,
   но правило их изменения НЕ установлено, и «по виду сущности» они не группируются — см.
   «[Старшие байты `Flags`](#старшие-байты-flags--правило-не-установлено)». Читать полем шире байта
   нечем подтвердить.
3. **Смысл `nameId`.** Известно, чем он не является. Чем он является — не установлено, и
   разница ровно `0x100` внутри пары объяснения тоже не получила. У `BaseEvents` и
   `InteractionAction` бóльшее значение пришлось на сундуки; у `StateMachine`, `Positioned` и
   `Life` владельцы обеих половин не разобраны, так что даже правило «у сундуков больше» — не
   правило, а два случая из пяти.
4. **Один компонент вне таблицы** у одной сущности из пятидесяти. Не объяснён. Отдельно, уже по
   всей выборке: **1609 проходов, 284312 просмотров сущностей, неопознанных vtable ровно четыре.**
   Что это за четыре — не установлено.
5. **vtable не добрана** — после добора до 40 пар остались `Shrine` и `Monolith`. Причина та же и
   она не техническая: **сущностей такого вида в заходах не было**; зона со святилищем нужна
   отдельно. Городской заход и заход с брошенными вещами закрыли `Portal`, `NPC` и все девять
   предметных компонентов; бой закрыл `DiesAfterTime`. Список назван поимённо потому, что эти типы
   отслеживаются; он **не** полон: всё, чего нет в таблице из 40 пар, незамерено ровно так же —
   `Charges`, `Flask`, `Map`, `SkillGem`, `TimerComponent`, `ClientBetrayalChoice` и остальные
   классы из `Core/PoEMemory/Components/`.
6. **`0x35DFB80` — коллизия, которую нечем разрешить.** Оракул называет её `AttributeRequirements`
   у брони и оружия и `Usable` у валюты; vtable одна, значит одно из имён неверно, и какое —
   не установлено. Пара **не внесена**. Это второй известный случай ошибки самого оракула.
7. **`0x35A5C68` (`nameId 0x11E`) — компонент без имени** на `Metadata/Effects/Effect`: оракул его
   не назвал, и подставить имя нечем.
8. **`Projectile` держится на косвенных доводах**, а не на поадресном соединении: живого снаряда
   оракул не застал за три попытки в одном бою. Пара помечена слабой; переснять при первом же
   бою, где оракул снаряд увидит.
9. **RVA привязаны к этой сборке.** Устойчивость таблицы «тип → vtable» между патчами не
   проверялась, и проверить её можно только на другой сборке.
10. **Перезапуска не было.** Числа сняты четырьмя заходами **одного дня** — «The Reliquary»,
    брошенные вещи, бой, город, — то есть больше чем в одной зоне, но при **одной и той же базе
    модуля** `0x7FF78FCD0000`. Смена зоны таблицу не сдвинула; **ASLR здесь НЕ закрыта**, в отличие
    от `IngameData`, где числа пережили полный перезапуск клиента.
11. **Полей `Pathfinding` никто не читал** — в таблице есть только его vtable. Это намеренно,
    см. «Чего НЕ делать» в [плане](../plan/ROADMAP_PROMPT.md).
12. **`Reaction` сужен, но не решён** — три байта-кандидата в одном qword, выбрать нечем,
    см. «[Сужено, но НЕ закрыто](#сужено-но-не-закрыто)».
13. **Поля новых компонентов** (`AreaTransition`, `MinimapIcon`, `StateMachine`,
    `TriggerableBlockage`, `HideoutDoodad`, `PetAi`, `Portal`, `NPC`, `DiesAfterTime`, `Brackets`,
    `Functions` и все девять предметных) не читались: замерена только их vtable, то есть факт
    «компонент этого типа здесь есть». Для маркеров без полей (`DiesAfterTime`) это и есть всё
    содержимое типа; для `Mods`, `Base`, `Sockets`, `Stack`, `Quality`, `Weapon`, `Armour` —
    далеко не всё, и их `[FieldOffset]` по-прежнему эталонные.
14. **У `Brackets`, `Functions`, `LocalStats` и `Projectile` в форке нет классов** — vtable
    замерена, спрашивать их некому. Это не пробел замера, а замечание о том, что пара в таблице
    сама по себе ничего не включает.
15. **Замер не трогал**: поля `Targetable`, поля `Mods`/`WorldItem` (у `WorldItem` замерено ровно
    одно поле — `+0x28`, путь к предметной сущности), `Render.Height` и `Render.MeshRotation`
    (их числа есть только в обследовании и не переподтверждены), весь слой UI, остальную
    `ServerData`, файлы.

## Что должен сделать владелец

Остаток упирается не в код, а в то, что **нужных сущностей не было в зоне**. Ниже — что именно
надо сделать в игре, сгруппированное **по заходам**, а не по полям: один заход закрывает сразу
несколько строк из списка выше. В каждом пункте — где встать, что запустить и что считается
успехом.

**ЧТО УЖЕ ЗАКРЫТО — три захода из прежнего списка сделаны.**

* **Брошенные вещи** (14 штук: валюта, дивинационная карта, ботинки, топор, посох, коготь, шлем) —
  дали все девять предметных компонентов и, отдельно, замер пути `WorldItem + 0x28`, 14 из 14.
  Заодно снята прежняя строка «нужна доработка инструмента»: спуск в предметную сущность больше
  не гипотетический, путь к ней замерен.
* **Бой** — дал `DiesAfterTime` (дважды идентично) и четыре коллизии `nameId` разом, включая
  `Positioned` и `Life`. `Projectile` этим заходом закрыт **не полностью**: живого снаряда оракул
  не застал, пара стоит на косвенных доводах и помечена слабой.
* **Город** — дал `Portal`, `NPC`, `Brackets`, `Functions`.

**ЧТО ОСТАЛОСЬ — два захода за числами и один проверочный.**

Одна просьба заходом не ограничена и делается где угодно: **`InventoryId`**. Снять
`RefLive --as Entity <адрес сущности>` на игроке и на паре сущностей — это даёт истинное значение,
от которого можно искать поле. Выборкой его искать нельзя: она уже один раз согласилась на трёх
сущностях и ошиблась.

### Заход 1 — зона со святилищем

Закрывает: `Shrine`. Больше ничем его закрыть нельзя — святилища не было ни в одном из четырёх
заходов.

1. Зайти в зону, где есть **святилище** (shrine), и не активировать его до снятия дампа.
2. Снять `RefLive --harvest 200`.
3. Успех: в выдаче появилось имя `Shrine` ровно с одним RVA. Попутно, если в зоне окажется
   `Monolith`, — закроется и он.

### Заход 2 — СОЮЗНЫЙ монстр (единственное, что закрывает `Reaction`)

Закрывает: `Reaction` — и только он. Ни враждебный монстр, ни пет этого не делают: у союзного
монстра «фракция» и «булев признак враждебности» **обязаны разойтись**, а сейчас в одном qword
лежат три кандидата — `+0x1E0`, `+0x1E2`, `+0x1E3`, — и разделить их нечем.

1. Иметь рядом **союзную сущность с компонентом `Monster`** — призванного миньона, спектра или
   квестового союзника.
2. Снять `RefLive --harvest 200` и **сырой дамп `Positioned`** этой союзной сущности.
3. Тем же заходом, если в бою будут **летящие снаряды** и оракул застанет снаряд живым, —
   переснять `Projectile` поадресным соединением и снять с пары пометку «слабая».
4. Успех по `Reaction`: спросить у оракула его `Reaction` для союзника и сравнить с байтами
   `+0x1E0`, `+0x1E2`, `+0x1E3`. Поле — тот байт, который совпал с оракулом **и** на союзнике,
   **и** на враждебных монстрах, **и** на игроке. Если у союзника все три байта совпали с тем,
   что дают враждебные монстры, случай опять ничего не разделил — нужен союзник другого вида.
   Отдельно учесть: `+0x1E0` и `+0x1E2` могут снова совпасть между собой. Тогда выбор поля
   сузится до двух байт-близнецов, и это надо будет так и записать — «любой из двух даёт то же
   значение», а не выдавать один из них за найденный.

### Заход 3 — перезапуск клиента

Закрывает: не поле, а **свойство всех чисел этого документа**. Смена зоны таблицу уже не сдвинула —
четыре захода прошли в разных местах, включая город, — но **база модуля во всех четырёх была одна
и та же**, `0x7FF78FCD0000`. Значит ASLR не проверена.

1. Полностью перезапустить клиент (новая база модуля, ASLR), зайти в **другую** зону.
2. Снять `RefLive --harvest 200` ещё раз.
3. Успех: те же имена дают те же **RVA** (не абсолютные адреса). Это то, чего у слоя
   сущностей сейчас нет и чего у `IngameData` — четыре зоны и перезапуск — уже есть.
4. Расхождение хотя бы в одной паре означает, что таблица «тип → RVA vtable» привязана не только
   к сборке, но и к запуску, и модель надо пересматривать, а не дополнять.

Устойчивость между **патчами** этим не проверяется: для неё нужна другая сборка игры, и раньше
следующего патча такой проверки не будет.

## Перепись по популяции — приём, добавленный 2026‑09‑17

> Клиент `PathOfExile_KG` pid 24676, база модуля `0x7FF78FCD0000`, зона акта 5 уровня 48
> (хэш `0x44CEA8A9`), 195–197 сущностей, из них 59 монстров. Инструмент — `tools/EntCap --census`.

### Зачем понадобился ещё один приём

Всё, чем закрывался слой сущностей до сих пор, проверяло ПОДСТАВЛЕННОЕ число: берём гипотезу,
читаем по ней, смотрим, сошёлся ли критерий. У этого есть предел, и он назван в самом промте —
«выборка из трёх сущностей не выборка»: `InventoryId +0x70` сошёлся на трёх и развалился на сорока.
Оракул от этого не спасает, потому что его ответ — тоже выборка из ОДНОЙ сущности.

Перепись устроена наоборот: она не проверяет смещение, а **ищет** его, и материалом ей служит
не одна сущность, а вся зона.

    EntCap.exe --igs <адрес> --census <RVA vtable> [--census-bytes N]

Компонент собирается со ВСЕХ сущностей зоны (опознаётся по собственной vtable, слот-таблица не
нужна), и по каждому смещению окна печатается, что это смещение делает на всей популяции:

* **строго булевы и непостоянные байты** — кандидаты в признаки, с разбивкой по видам сущностей;
* **постоянные по всей зоне байты** — карта «здесь поля нет»: одинаковое у монстра, сундука и
  декорации не может быть признаком сущности;
* **малые целые** — кандидаты в перечисления, с гистограммой значений;
* **векторы** `First/Last/End` — с гистограммой числа элементов.

Шаблон вектора узок намеренно: требуется `First <= Last <= End`, все три либо нули, либо
канонические указатели, и `(Last − First)` кратно 8. По всей популяции случайные 24 байта этого
не выполняют. Вектор ценен не сам по себе, а как ЯКОРЬ: рядом с ним лежит то, что он описывает.

### Первое применение: `Targetable` — ЗАКРЫТ

Объявлено было `isTargetable 0x30`, `isTargeted 0x32`. Перепись по 71 компоненту в шести видах
сущностей:

* `0x30..0x34` **не булевы вовсе** — там значения больше 1. C# маршалит любой ненулевой байт в
  `true`, поэтому прежний `isTargetable` отвечал «да» почти на всё. Это хуже, чем не отвечать:
  ложное `true` в точке вызова неотличимо от настоящего;
* **в голове компонента строго булевых и непостоянных байт ровно ДВА**: `0x50` и `0x51`.

> **Поправка к первой редакции этого раздела, и она про метод, а не про число.** Сначала здесь было
> написано «строго булевых и непостоянных байт во всём окне 128 — ровно два». Это утверждение про
> окно в 128 байт, а не про компонент. При окне 2048 таких байт **пятьдесят пять**.
>
> Лишние не разбросаны: компонент несёт ПОВТОРЯЮЩУЮСЯ подструктуру с шагом `0x90` — прогоны по 48
> булевых байт начинаются на `0xE0`, `0x170`, `0x200`, `0x290`, `0x320`, `0x440`, и в каждом одни и
> те же пять непостоянных позиций. Это массив записей, а не набор признаков.
>
> Это **ловушка радиуса, за которую уже было заплачено на камере** (там двойник `Width/Height` лежал
> за границей `0x400`), и она повторилась через несколько часов после того, как была записана в
> список ловушек. Записать ловушку недостаточно: инструмент должен мешать в неё попасть. Поэтому
> окно по умолчанию у переписи поднято, а разбор `--census-bytes` починен — он читался десятичным,
> тогда как соседний `--census` шестнадцатеричным, и `--census-bytes 0x800` молча давал 256.
>
> Уцелевшее утверждение уже, и оно то самое, которое нужно: в ГОЛОВЕ компонента — в 74-байтовом
> прогоне булевых от `0x36` до `0x7F` — непостоянных ровно два, `0x50` и `0x51`.

Оракул развести их не может: спрошенный про монстра, он отвечает `isTargetable True,
isTargeted False`, и **оба** кандидата дают ровно это, потому что у монстра там единица.

Развели их сущности, на которых кандидаты расходятся, — их пять из 71, и инструмент печатает их
поимённо:

    +0x50  +0x51   путь метаданных
    0     1      Metadata/Chests/Pot4v2
    0     1      Metadata/Chests/Pot4v1
    0     1      Metadata/Chests/Pot4v1
    0     1      Metadata/Chests/Pot4v2
    0     1      Metadata/Pet/ScientistLabRat/ScientistLabRat

Четыре разбиваемых горшка и косметический пет. При `0x50` они все `false`, при `0x51` все `true` —
то есть `0x51` строго шире.

Кем именно они друг другу приходятся, говорит **унаследованная раскладка**
`GameOffsets/Components/Targetable.cs`: она объявляет подряд `IsTargetable`, `IsHighlightable`,
`IsTargetted`. Горшок и косметический пет — ровно то, что обводкой подсвечивается, но целью по клику
не берётся. ПОРЯДОК полей — это форма, а форму промт у эталона брать разрешает; числа — нет. Так что
назначение держится на замеренном отношении широты плюс унаследованном порядке, и опровергается
показом того, что горшок кликом нацеливается.

**Структурный довод, который был проверен и НЕ ПРОШЁЛ** — записан, потому что неудавшаяся проверка
это тоже результат. Если бы блок просто уехал на `+0x20`, унаследованный `UnknownPtr0@0x28` оказался
бы на `0x48` и обязан был бы быть каноническим указателем у каждого носителя. Он им не является:
`0x48..0x4F` попадают внутрь булевого прогона, то есть каждый байт там 0 или 1 у всех. Блок НЕ
сдвинулся целиком, и опираться на «старое `0x32` стало `0x52`» нельзя.

Разбивка по видам при `0x50`: монстры 58 из 59, разные объекты 5 из 5, игрок 1 из 1, святилище
1 из 1, горшки 0 из 4, пет 0 из 1.

`isTargeted` на `0x52` — **НЕ ЗАМЕРЕН, это заглушка**, и после провала структурного довода у него
не осталось опоры вовсе. Известно только отрицательное: целью может быть не более ОДНОЙ сущности
зоны, а `0x51` истинен почти у всех, значит `0x51` — не он. По `0x52` лежит ноль по всей зоне, но
таких байт в прогоне `0x36..0x7F` десятки, и ничем замеренным `0x52` от них не отличается.

Стоит развести его одно движение курсора БЕЗ клика: навести на монстра и повторить перепись. Признак
самоопознаётся, потому что критерий — **единственность**, а не значение: ровно один носитель обязан
стать единицей, и это обязан быть тот, на ком курсор. Ни форк, ни автопилот это свойство сегодня не
читают (`isTargetable` читается в пяти местах и от него не зависит), поэтому заглушка ничего не
стоит, пока помечена.

### Второе применение: `ObjectMagicProperties.Rarity` — СУЖЕН, НЕ ЗАКРЫТ

64 сущности несут этот компонент (59 монстров, 4 сундука, святилище).

Байта со значениями `{0,1,2,3}` в окне 768 байт **нет вовсе**. Единственные кандидаты-перечисления
принимают лишь два значения: `+0x45` даёт `0 x36 / 2 x28`, а `+0x16D`, `+0x175`, `+0x17D` дают
`0 x39 / 2 x25`.

Векторы дали сцепку:

    +0x168   0 x39   7 x24   14 x1
    +0x210   0 x39   2 x22   3 x2   5 x1
    +0x228   0 x61   13 x3

Те же 39 сущностей, у которых `+0x16D` равен нулю, имеют ПУСТЫЕ векторы `+0x168` и `+0x210`;
у остальных 25 векторы непусты. То есть `+0x16D` отличает «есть модификаторы» от «нет», а это и
есть смысл редкости выше обычной.

**Но какое ЧИСЛО какой редкости соответствует, памятью не различить.** В этой зоне встретились
только две редкости, и значение `2` при `{Normal 0, Magic 1, Rare 2, Unique 3}` означало бы, что
25 из 64 — редкие, что для одной зоны многовато. Нужен факт ВНЕ памяти: зона, где в кадре есть
И редкий (жёлтое имя), И магический (синее) монстр. Это уточняет просьбу №1 владельцу и до неё
число не вносится.

### Что приём даёт дальше
