# Паритет с ExileApi‑Compiled — измеренная база

> Снято 2026‑09‑14 против **реальной установки** `C:\Users\ReviPc\Desktop\ExileApi-Compiled`
> (ExileCore `1.0.0+fcb9ae4…`), а не против реконструкции DLL.
> Соседний документ [compatibility-exileapi-compiled.md](compatibility-exileapi-compiled.md)
> выведен из реконструкции и остаётся полезным как разбор *почему*; этот — как **счётчик**.

## Как перепроверить

```bash
dotnet build -c Release ExileApi.sln     # сборка ложится в ..\..\PoeHelper
tools/parity.sh                          # счётчик
tools/parity.sh ../PoeHelper --full      # вся таблица построчно
```

Ненулевой код возврата — не ошибка сборки, а остаток работы.

Карта поверхности — `tools/ForkProbe/surface.json`: **753 единицы данных, 3690 членов,
388 типов**, по 14 областям, у каждой записи путь доступа, состояние заполнения, цена чтения и
ценность для внешнего потребителя. Проверяется зондом по метаданным (`tools/ForkProbe`), игра не
нужна. Флаг `requireAll` означает, что строка краснеет при пропаже ЛЮБОГО члена набора, а не
«хотя бы одного из кандидатов».

## Что из этого переносится без реверса, а что нет

Классификация 173 отсутствующих типов по базовому типу в эталоне:

| база | сколько | требует ли оффсетов |
|---|---:|---|
| `Enum` | 32 | **нет** — чистый перенос значений |
| `Object` (простые классы, обёртки, настройки) | ~127 | **в основном нет** |
| `RemoteMemoryObject` / `Element` / `Component` | ~131 | **да** — каждый читает память |
| `ValueType` (структуры `*Offsets`) | ~64 | **это и есть оффсеты** |
| `UniversalFileWrapper<T>` (таблицы `.dat`) | 5 | да, плюс схема записи |

## Главный факт: оффсеты между форками НЕ переносятся

Сравнение числовых смещений полей двух сборок `GameOffsets` (`tools/OffsetDiff`, маршалируемая
раскладка через `Marshal.OffsetOf`):

```
эталон: 126 структур        этот форк: 122 структуры
общих структур по имени:    35
общих полей:                121  →  совпало 35, РАЗОШЛОСЬ 86
структур с полным совпадением: 8
```

Расхождения не «на пару байт», а структурные. Пример — компонент жизни:

| | эталон | этот форк |
|---|---|---|
| `Owner` | `0x00` | `0x08` |
| жизнь | `Health : VitalStruct` @ `0x48` | `MaxHP` @ `0x154`, `CurHP` @ `0x15C` |
| размер | `0x68` | > `0x160` |

То есть эталон моделирует Life как `Owner` + три `VitalStruct` по `0x20`, а этот форк — как плоский
набор полей в совсем другом диапазоне. Это разные модели ОДНОЙ памяти, снятые с разных сборок игры.

**Следствие для работы.** Паритет распадается на две принципиально разные половины:

1. **Поверхность API** — типы, члены, сигнатуры, значения enum. Переносится чтением эталона;
   проверяется `tools/parity.sh` без игры. Сюда попадают все 32 enum и большая часть простых классов.
2. **Числа** — смещения, по которым эти члены читают память. **Не переносятся.** Их придётся
   снимать под тот патч игры, который запущен, и проверять они могут быть только живой игрой.

Дописать 193 типа поверх основания, числа которого не проверены на текущем патче, — значит получить
193 типа, стабильно возвращающих мусор, и не узнать об этом, потому что счётчик паритета станет
зелёным. Счётчик проверяет НАЛИЧИЕ члена, а не правильность значения; это его граница, и её надо
держать в голове.

## Второе доказательство: нумерация enum тоже от другого патча

`tools/enumdiff.py` сверяет ЗНАЧЕНИЯ enum, а не только наличие членов — счётчик паритета такую
поломку не видит в принципе.

```bash
python tools/enumdiff.py            # все enum, объявленные в этом форке
python tools/enumdiff.py --strict   # ненулевой код при любом расхождении
```

Результат на 2026‑09‑14: **сверено 72, расходятся 10** —
`AnimationE`, `EntityType`, `GameStat`, `InventoryIndex`, `InventoryTypeE`, `LeagueType`,
`MapIconsIndex`, `ModDomain`, `Offsets`, `Windows`.

|---|---:|---:|---|
| `GameStat` | 10 613 | 23 339 | 13 043 члена нет, у 10 148 общих ДРУГИЕ числа (сдвиг +34…+39) |
| `EntityType` | 35 | 39 | 27 членов из 35 сдвинуты на 1 |
| `MapIconsIndex` | 206 | 700 | `LootFilter*` переехали с 53… на 225… |
| `InventoryIndex` | 15 | 45 | сдвиг на +5 (вставлены новые слоты) |

Последняя строка — самая показательная: это не «другие имена», а **компонент `Render` вырос на 8
байт** между сборками игры. Ровно то же видно и в структурах (`tools/OffsetDiff`).

Вывод: расхождение не локальное и не косметическое. **Два форка нацелены на разные сборки игры**,
и это проявляется одинаково в трёх независимых местах: смещения структур, числовые индексы статов
и порядковые номера типов сущностей.

### Чем это кончилось при первой попытке переноса

Механический перенос 12 существующих enum «добавить недостающие члены из эталона, существующие не
трогать» дал **6 внутренне противоречивых enum**: два имени на одно значение
(`InventoryIndex`: `Helm=1` и `Unknown1=1`; `MapIconsIndex`: 87 таких пар; `AnimationE`,
`InventoryTypeE`, `ModDomain`, `InventoryTabType`). Это откачено.

Перенос сохранён только там, где нумерация уже совпадала и сверка даёт ноль расхождений и ноль
дублей: `ItemRarity`, `InventorySlotE`, `InventoryType`, `InventoryTabMapSeries`, `ModType`,
`FontAlign`.

**Правило, которое из этого следует:** нельзя дописывать члены с эталонной нумерацией в enum,
чья существующая нумерация от другой сборки. Либо enum переносится ЦЕЛИКОМ (и тогда это решение
сменить целевую сборку игры), либо не трогается вовсе.

### Оговорка к 25 новым enum

Созданные с нуля типы несут ЭТАЛОННУЮ нумерацию — иначе их создать неоткуда. Для тех из них, что
не индексируют игровые данные (`MemoryBackendMode`, `SocketColor`, `BanditType`, `HeistJobE`,
`ShortcutModifier`, `ShortcutUsage`, `SocialTabTypes`, `VisibleSubMap`, `InstanceType`,
`PartyPlayerInfoType`, `SkillGem*`, `Influence*`, `HoverItemState`, `GameStateTypes`,
`InvitesPanelItemKind`, `BetrayalRelationshipStatus`, `ElementType`, `ElementFlags`,
`EntityFlags`, `InventoryTabAffinity`, `SentinelState`) это безразлично: их значения задаёт
ExileCore, а не игра.

Для тех, что индексируют игровые данные, — прежде всего `QuestFlag` (3999 членов) и
`InventoryNameE` — эталонная нумерация верна только для эталонной сборки игры. Если этот форк
останется на своей сборке, их придётся пересчитывать.

## Порядок, который из этого следует

1. **Сначала доказать, что основание читает текущий патч.** Пока это не сделано, любая цифра
   паритета переоценивает готовность. Проверяется прогоном в игре и сверкой значений с эталоном —
   оба форка читают один процесс, поэтому расхождение значения видно напрямую.
2. **Потом — половина «поверхность»**: enum'ы и простые классы (около 160 типов), они не зависят
   от оффсетов и закрываются механически.
3. **Потом — половина «числа»**, по подсистемам, каждая со своей проверкой в игре.

## Чего счётчик НЕ говорит

* **Правильность значений.** Строка зелёная, если член есть; читает ли он то, что надо, знает
  только игра.
* **Поведение.** Тела методов эталона обфусцированы (ILSpy не восстанавливает: перепутанные стеки,
  вырезанные `ldfld`/`call`, испорченные операнды переходов), поэтому «как эталон это вычисляет» —
  недоступно. Совпадение сигнатуры не означает совпадения поведения.
* **Нужность.** 512 незакрытых строк — это ширина эталонного дистрибутива, а не список блокеров.
  Для сравнения: плагин `MovementHelperPoe` (autopilot, 1036 файлов) **собирается против этого
  форка с нулём ошибок** — вся поверхность, которая ему нужна, уже есть.
